# 研究库 Interface 审查

2026-11-14。三项 Module 基线与相关产品行为已确认。本文件展开研究库的候选 Interface 与数据契约，供整体技术方案核对；尚未修改生产代码。总体见[技术方案](display-app-technical-plan.md)，阅读位置含义见[阅读核心 Interface](reader-core-interface.md)。

## 一句话职责

将 Mac 发布到 iCloud 的成果变成一份明确、完整、可打开的研究版本，并管理个人记录的可靠存取。Reader 决定内容位置是否有效；研究库不重新判断焦点、章节或引用关系。

## 对调用者提供什么

| Interface | 契约 |
| --- | --- |
| `connectionState` | 未关联、核对目录、已关联或需重新关联；已关联不代表联网或全部文件已下载 |
| `entries` | 公司、覆盖期间、截止日期、正式版本、各版本准备状态，以及该研究的继续阅读候选 |
| `recommendedContinuation` | 首页的推荐继续入口；由研究库选出，页面不自行按时间排序 |
| `recordState` | 本机受理、保存与云交换的独立状态，区分未保存与已保存但待同步 |
| `connect(folder)` | 关联系统文件界面选定的目录并保存授权，恢复后仍核对是否可访问 |
| `refresh()` | 分别发现研究成果和个人记录，两路失败互不阻断 |
| `retryPreparation(version)` | 只重试指定研究版本的准备，不重新同步全部阅读记录 |
| `retryRecords()` | 重试待保存及待交换的个人记录，不重新下载研究包 |
| `continueReading(study, using: choice?)` | 固定推荐或明确选择的候选及其原版本，再准备并恢复；不会改开最新版本 |
| `readVersion(readyVersion)` | 明确打开用户选择的完整就绪版本 |

打开结果区分：交付 Reader、指定版本当前无法就绪、无法打开及恢复方式，以及被后续打开意图取代。准备期间通过条目状态显示进展，不能先交付半可读 Reader。

同一窗口中的较新打开意图使旧打开请求失效。A 在准备时用户另开 B，A 后来完成也不能覆盖 B；异步结果关联打开请求身份，共同宿主只接收有效结果，普通页面不自己解决竞态。

`ContinuationChoice` 是研究库提供的明确候选值，包含精确研究版本和候选身份。显式选择后不能再被默认推荐覆盖；候选失效时说明原因并保留重新选择方式。

## 两条独立内部工作流

### 成果准备

```text
发现精确版本
→ 请求系统提供文件
→ 私有候选目录
→ 核对清单、字节和研究绑定
→ 独立本机目录就绪
→ 提供有效研究输入
```

候选版本不覆盖已就绪目录。当前正式版本在准备途中又变更，也不改变本次已固定的准备对象；完成 V2 不要求重新追逐 V3。活动 Reader、PDF 请求和异步读取始终使用同一固定资源值。

首版保留已准备版本，不自动清理；因此不先创建通用缓存回收框架。原版本本机缺失时，可以从其正式分发包重新准备；云端也不可得则明确提示，仍允许打开其他可读研究。

### 个人记录

```text
接收带阅读发生时间的 checkpoint
→ 更新本机候选
→ 分配本设备单调序号并串行保存
→ 异步交换 iCloud 记录
```

发生时间在阅读核心接受真实阅读观察时保留，不能在保存或同步时重新计时。本机失败保留待写数据并说明尚未成功保存；本机成功但云失败则保持本机继续阅读，显示等待交换。旧写入完成不能覆盖较新记录。

各设备独立写自己的记录；接收其他设备数据时检查格式、身份与序号，去重并保留候选。一般按实际阅读时间推荐；离线且时钟存在歧义时允许读者改选，保留其他有效位置，不假装拥有严格全局时间顺序。

记录实现只排列外壳并可靠存取。场景、焦点、段落与原页是否合法由 Reader 在指定研究中检查；位置候选和明确的用户选择一同交给 Reader，显式有效选择优先于默认推荐。

成果下载失败不阻断位置保存，记录同步失败不把完整研究变成不可读；二者只有共同目录授权与字节访问，不共享一个含糊的 loading/error 状态。

## 三份元数据的不同职责

Mac 在已有正式发布后形成分发包与轻量目录，不改变研究引擎、SQL 或财务规则。

| 数据 | 来源与含义 | 移动端如何使用 |
| --- | --- | --- |
| 正式 `snapshot.json` | 引擎正式快照；当前 schema 为 `cfa-research-snapshot/v1`，含快照身份、研究绑定及 `files` 的相对路径和 SHA-256 | 校验正式文件字节，保持研究与阅读稿、PDF 来自同一成果 |
| 派生 `resource-manifest.json` | 现有打包工具生成的 App 分发元信息；当前 schemaVersion 为 3，含文档路径、摘要、字节数、页数及数据集信息 | 核对分发清单与正式内容、来源声明及资源对应关系 |
| 轻量研究目录清单 | Mac 分发动作生成，列公司、版本、包位置、对应清单摘要及明确当前版本 | 用于发现版本；不能仅凭目录清单宣称包已就绪，也不按到达时间推断新版 |

`snapshotManifestSHA256` 对应 `snapshot.json` 文件字节摘要；`research.publication.manifest_sha256` 不是这个文件摘要，不能互相替换。当前打包器额外保留的 logo 属于 App 资源，不在正式 `snapshot.files` 内。

准备时检查完整文件、摘要及字节数，复用现有研究读取器核对正式身份、已复核状态和图解的研究字节绑定，并核对来源页码声明。PDF 实际加载、物理页访问和高亮由 PDFKit 集成验证；不在 Core 再造一个 PDF 解析器。

既有打包工具在 Mac 上以单一 Study 目录替换并删除备份；移动端不能照搬这个最终替换步骤，必须保存独立版本目录。分发出的单份版本内容与元信息固定，不对在用版本原地更新。

事实依据：[现有打包工具](../ios/CompanyLens/Tools/prepare_resources.py)、[正式快照](../ios/CompanyLens/Study/snapshot.json)、[派生资源清单](../ios/CompanyLens/Study/resource-manifest.json)。

## 单向依赖与系统适配

Library 使用 Reading 定义的有效研究、位置候选和 checkpoint 契约来创建 Reader，Reader 不导入 Library。Library 不重新实现语义恢复。

Library 定义窄的 `CloudFolder` Interface，App/Platform 的生产实现负责授权、协调访问和系统文件可用性，由组合入口注入。测试实现脚本化部分文件、失效授权与迟到记录；准备、重试和排序政策留在 Library，不藏进假适配。

真实本机文件采用临时目录验证，不为每个文件操作添加一层协议。系统目录选择留在平台代码，不把 UIKit 或 App 类型导入 Core。

## 三条完整流程

1. **发现新版**：目录出现 V2 → 显示准备 → 候选目录与完整验证 → V2 独立就绪。V1 仍在阅读且目录有效；用户明确打开 V2 才创建新 Reader。
2. **继续缺失的原版本**：候选指 V1 → 尝试准备 V1 → 不可得则显示原因和重试，不改开 V2。成功后只传 V1 的位置候选给 Reader。
3. **记录失败**：本机失败保留待写项；云失败保留本机已保存位置。重试记录不下载资料，重试资料不重新写全部进度。活动 Reader 不因云记录到达而跳转。

## 修改落点与验收

资料发现、完整性和重试改成果准备；位置外壳排序、保存及交换改记录实现；系统授权与物化错误映射改 FileProvider 适配。业务页面不参与这些顺序。

验证需覆盖：部分文件到达及错摘要不进入就绪、旧版 Reader 持续可读、打开请求被取代、原版本不可得、明确候选不被推荐覆盖、串行保存防旧覆盖、本机失败与云失败分开，以及授权失效仍可读本机已准备研究。

这是技术契约文档，本轮未执行新增实现、云同步或真实设备测试。
